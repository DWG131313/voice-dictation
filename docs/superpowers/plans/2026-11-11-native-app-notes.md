## Findings

- Task 11 (fix round 1): new in the store, for Tasks 18, 19 and 21. `Transcript.rawModelKey` and `rawTranscribeSeconds` keep the dictation's own model and time; they are set when the transcript is made and never change. `AlternateResult.wasMain` marks a main text that `promote` or `revertToRaw` set aside. `AlternateResult.editedFromModelKey` names the model whose text a set-aside hand edit was. `TranscriptStore.Health` gains `.recovered(String)`. The Task 11 bullets below describe the rules as they now stand.
- Task 11: What later tasks can rely on from `TranscriptStore` (`Store/`).
  - Every finished dictation is kept, failed and skipped ones too: `pipeline.onOutcome` feeds `store.add` beside the comparison writer. The old Preferences window's "Keep transcription history" checkbox no longer stops that; it only hides the menu's Recent Transcriptions. On this laptop it was never turned off (the old app's defaults hold only `hasLaunchedBefore`).
  - The menu's Recent Transcriptions lists `store.search("", scope: .all).prefix(10)`; a failed dictation shows greyed out as "Failed — <reason>". "Clear History" is gone: against the store it would delete every transcript, imported history included, with one click and no undo, and the spec deletes transcripts one at a time in the window (Task 19). Task 13 replaces this menu anyway.
  - `search` matches the main `text` only, not `rawText`, ignoring case and accents (`localizedStandardContains`), newest first. An empty query matches all; `.today` means since local midnight.
  - `latest` is the newest transcript that has text, so Paste last (Task 23) skips a failed dictation, as the pipeline's in-memory `pasteLast` does today.
  - `addAlternate` keeps one re-transcription per model: a newer result from the same model replaces that model's earlier re-transcription in place. That is Task 19's `testRetranscribeSameModelTwiceReplacesNotDuplicates`, settled here because Task 19's file list does not include `TranscriptStore.swift`. It never replaces a main text that was set aside (`wasMain`), such as the pasted text. So a transcript can hold a set-aside text and a re-transcription from the same model side by side, and Task 19's comparison should tell them apart.
  - `promote` makes the alternate the main text, with its model and time. The alternate is removed, and the old main text is set aside as a new alternate with `wasMain` true, or dropped when it is empty, as for a failed dictation. A set-aside hand edit has `modelKey` `"edited"` and `editedFromModelKey` set to the model whose text Danny edited. Promoting such an edit back makes it the main text again with `isEdited` true. Its `modelKey` is the model whose text he edited. Should an `"edited"` alternate lack `editedFromModelKey` (only one made outside the store could), the dictation's own model and time stand in. Any other promote clears `isEdited`. So `modelKey` always names a real model that `ModelID(storageKey:)` parses (Task 18's Model fact), and an edit shows as Edited wherever it is the main text (Task 19). `rawText`, `cleanedText`, the dictation's own model and time, `date` and the status are untouched. A re-transcribed failed transcript stays Failed until Task 19 changes its status. `promote` deletes the promoted `AlternateResult` rather than rewriting it, so a caller still holding that object after the save is reading a deleted model: Task 19 must re-read `t.alternates` after a promote. A main text already held by another `wasMain` alternate is not set aside again, so promote and revert rounds add no copies.
  - `revertToRaw` makes `rawText` the main text with the dictation's own model and time, and clears `isEdited`. The main text it replaces is set aside first as a `wasMain` alternate, so nothing is lost, unless it is blank, a `wasMain` alternate already holds the same text, or it is just the dictation's own `rawText` or `cleanedText` (the transcript keeps both, so Task 21's Raw/Cleaned switch adds no alternate on a flip). So a promoted re-transcription (even by the dictation's own model), a hand edit (kept as `"edited"`, with `editedFromModelKey` the model whose text was edited, the dictation's own included) and a pasted text of other wording are all kept. Revert does nothing when `rawText` is empty (a failed dictation), so it cannot empty a text that a re-transcription gave it.
  - `AlternateResult.date` is when the result became an alternate. The relationship has no order, so sort by it.
  - Every change is saved at once; a failed save is logged and rolled back. The store never syncs (`cloudKitDatabase: .none`).
  - When the store cannot be opened, whichever of `transcripts.store`, `-wal` and `-shm` exist are renamed with one `.broken-yyyyMMdd-HHmmss` suffix (local time), the journals first and the database last. A new, empty store then starts at the same path at once (Ruling T11-3). `health` is `.recovered(<sentence>)`: the store works and every dictation is kept, so the window (Task 18) should show the sentence as a notice beside the list, not in its place. It reads like "Your earlier history could not be opened, so it was moved aside and a new one started. Its files are in ~/Library/Application Support/VoiceDictation as transcripts.store-wal.broken-20261112-153012, transcripts.store-shm.broken-20261112-153012, and transcripts.store.broken-20261112-153012."
  - `health` is `.unavailable(<sentence>)` (no `container`, `add` returns nil, `search` finds nothing) only when no store can be had. That is when there was nothing to move aside (for example, the store's folder cannot be made), a rename failed, or the new store failed too. Task 18's "store unavailable" empty state is this case. A failed rename leaves the database under its own name, because the journals go first. So no new store ever starts beside a leftover journal, and the next launch moves the rest. With the database renamed first, as before this fix, a test saw exactly that: after a half-finished move, the next open silently started a new store beside the leftover `-shm`.

- Task 9 (fix round 1): The app's own Cmd+V is tagged. `PasteEngine` sets `.eventSourceUserData` to `PasteEngine.eventTag` ("VDPASTE" in ASCII) on the key-down and key-up it posts. The Globe key's event tap passes a tagged key-down through without consulting the press (`GlobeKeyStrategy.action(forKeyDown:sourceUserData:presses:)`). This is needed because the pipeline pastes a dictation as soon as its text is ready, which can be while the hotkey is held for the next one, and the tap sees that Cmd+V like any other key. Task 23's `ModifierKeyStrategy` must keep the rule for every hotkey choice, including while hands-free is locked. Paste last goes through `PasteEngine`, so it is tagged too. - Task 9: What later tasks can rely on from `DictationPipeline`.
  - It does not clean up or apply replacements yet; it stores `cleaner` and `replacements` unused. Task 21 adds the cleanup step. `Replacements.apply` only arrives in Task 22, and Task 22's file list does not include `DictationPipeline.swift`, so whichever of them adds that function must also add the call, between the service's text and the cleaner. Task 9 passes `vocabulary()` to the service with each dictation.
  - Dictations go to the service as soon as each recording ends, so the service always sees every dictation in line and keeps re-transcriptions behind them. The pipeline pastes in recording order. When a fifth arrives with three waiting, the second-oldest in line is skipped. Its call to the service is cancelled while it waits, so its outcome (Failed, with the clip and "Skipped: too many dictations waiting") comes a moment later, usually before the outcome of the dictation being transcribed. One narrow case is kept by ruling, because its window is one main-actor hop. The pipeline counts the dictation at the head of its line as being transcribed until it has taken that dictation's result on the main thread. A fifth recording that ends after the service has returned the head's result, but before the pipeline has taken it, still skips the second in line. Yet only three are then waiting at the service, and the skipped dictation is already in the engine. So the effect is a skip that should not happen, of a clip that has already reached the engine.
  - Two cancels. The hotkey uses `cancelHold()`: a key pressed while Globe is held (Globe+Right Arrow, or Escape) cancels this hold's dictation and nothing else. That is the recording under way or, when the recorder ended the recording by itself while Globe stayed down (300 s, or an input change), the dictation it became, until Globe goes up. After a failed start, or a recording the recorder threw away, it cancels nothing. So Globe+Right Arrow never stops an earlier dictation from pasting. `cancel()` is for Task 23's Escape while working: while recording it cancels only that recording; otherwise it cancels every dictation in line.
  - `missingPermission` (set by the app from `PermissionManager`) is what the state falls back to after an error. `selectModel(_:named:downloadingFirst:)` shows `.preparingModel(name)` while a model downloads and loads. A failure there is shown as an error and rethrown, and the caller saves the choice only on success.
  - An outcome's `date` is when its recording ended; the comparison file name uses it, as Task 2's did. `appName` is the frontmost app when the dictation finished: at the paste, or for a failure when it failed.
  - Comparison recordings (Rulings T9-1, T9-2): while the setting is on, every dictation that was not cancelled leaves a `<ms stem>.wav` and `<ms stem>.txt`, as Task 2's writer did. One with an outcome is written from `onOutcome`, its `.txt` holding the outcome's `rawText` (empty for a failure). A dictation whose text came back empty has no outcome. The pipeline reports its clip and the time its recording ended through `onNothingHeard`, and its `.txt` is empty. If Task 24's audio archive must keep those clips too, it needs `onNothingHeard` as well as the outcomes.
  - SDK facts used for the wiring: `Observations` (Observation, macOS 26) yields the current value first, then each change, and merges changes made in one main-actor turn. A script on this SDK saw `[1, 2, 4]` for changes to 1, 2, then 3 and 4 in one turn. Conforming a main-actor class to a delegate protocol with `@preconcurrency` inserts no run-time isolation check in Swift 5 mode; it relies on the caller using the main thread, which the recorder and managers do.

- Task 8: What later tasks can rely on from `TranscriptionService`.
  - `elapsed` is the engine's time on the clip only. Waiting in line, waiting for the model to prepare, and an attempt a dictation stopped are not counted. If Task 9's `transcribeSeconds` should include a dictation's wait for a loading model, it needs its own clock.
  - A failed prepare is kept (`prepareFailure(of:)`, internal) and logged as `[SERVICE] Could not prepare …`, but it does not stick. The next dictation prepares the model again, so a model that becomes ready (for example after Apple's one-time Download) works without being chosen again.
  - `select` calls take effect one at a time, in call order.
  - Unloading is per engine (Ruling T8-1), and timed from the re-transcription lane (Ruling T8-2, fix round 1). An engine counts as in use from the moment a call for one of its models is made until that call returns, so a queued re-transcription keeps its engine loaded. An engine that holds a loaded model, is not in use and does not hold the selected model is idle only while no re-transcription is running or waiting; it is unloaded once it has been idle for `idleUnloadDelay`. So a run of re-transcriptions on several engines (Task 10's bench) keeps them all loaded until the lane empties, and they go `idleUnloadDelay` after that. `select` unloads the previous engine at once only when nothing is using it; otherwise the engine goes once it has been idle for the delay.

- Task 7 (fix round 1): deleting a model while it loaded made WhisperKit go to the network. The load kept running after `delete` removed the files. If it got past the Core ML loads once the tokenizer folder was gone, `ModelUtilities.loadTokenizer` fetched the tokenizer from huggingface.co and recreated that folder. - Task 7 (fix round 1): with its default padding, WhisperKit's `VADAudioChunker` drops whatever follows the last split when that is 1 s or less, so a clip over 30 s could lose its last word. It leaves out a final chunk of 1 s or less only when that chunk holds no voice (EnergyVAD finds none, or its peak is under the app's 0.01 floor), so a silent tail cannot decode to "you". With tiny.en, a 30.2 s clip split into 29.3 s and 0.93 s, the last 0.93 s holding a spoken "Yes.", came back ending in "Yes.".
