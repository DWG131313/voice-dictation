## Findings

- Task 6: No speech-recognition permission is needed. Both Apple models transcribed in plain processes and in the test runner while `SFSpeechRecognizer.authorizationStatus()` stayed "not determined"; nothing was requested and no prompt appeared. Apple's `SpeechAnalyzer` docs and WWDC25 session 277 ask only for microphone access, and Task 14's onboarding has no speech-recognition step, which fits.
- Task 6: macOS reserves the language files per app, not per Mac. `AssetInventory.status(forModules:)` reports `.supported` (shown as "Not downloaded") to any process that has not reserved en-US, even when the files are on disk and `installedLocales` lists `en_US`. `assetInstallationRequest(supporting:)` makes the reservation for the calling process; when the files are already present it returns nil at once and the status becomes `.installed`. So the app's Download button (Task 14) is needed once even on a Mac that already has the files, and finishes immediately there.
- Task 6: The four Apple tests that run a model (two sample tests, two cancellation tests) ran and passed on this laptop; none skipped. For that I reserved en-US once for the test runner (`com.apple.xctest`) by calling `AppleSpeechEngine().download` for both models from a temporary, uncommitted test. On another Mac they skip with "language files are not installed for this test process" until the same is done there: add a test that runs `try await AppleSpeechEngine().download(.appleSpeech) { _ in }` and the same for `.appleDictation`, run it once with `swift test --filter`, then move it out of the repo. macOS may drop a reservation an app has not used for a while; the tests then skip again.
- Task 6: Apple Speech ignores the vocabulary; Apple Dictation uses it. `setContext` accepts contextual strings for both, but `SpeechTranscriber` gave the same text with and without them in two runs ("Quixal and Zorvith"; "Swift Data", "Xcode Gen", "Whisper Kid"). `DictationTranscriber` turned "Quickel" into "Qwixl", "swift data" into "SwiftData" and "our Max" into "Argmax", as Apple's docs suggest (only its page mentions contextual strings). The engine passes the vocabulary to both, as planned; for Apple Speech, Danny's words reach the text only through replacements (Task 22).
- Task 6: With a vocabulary, Apple Dictation takes 70–115 ms longer per clip (spent in `prepareToAnalyze`), and sharing one `AnalysisContext` between analyzers does not avoid it. Apple Speech pays nothing extra. Worth knowing for Task 10's timings.
- Task 6: A finished analyzer cannot be reused: after `finalizeAndFinishThroughEndOfInput()`, `analyzeSequence` returns nil at once and analyzes nothing, as Apple's docs say. The engine builds a fresh transcriber and analyzer for every clip; with `.processLifetime` that costs 3–6 ms once the model is loaded (the first load takes about 90–145 ms).
- Task 6: An analyzer that was never prepared and is handed an input sequence with no buffers never ends its module's `results`, even after `cancelAndFinishNow()`. The engine returns "" for an empty clip without building an analyzer, and prepares every analyzer it builds. A prepared analyzer cancelled mid-clip ends its results at once.
- Task 6: Both models want 16 kHz mono 16-bit input here; the engine converts each clip's float samples once. Apple Speech sends one result per phrase, each after the first starting with its own space, so they join with no separator. Given 100 ms of a word, Apple Speech returned "Bye.", the kind of whole-transcript hallucination `OutputFilter` drops in the service (Ruling P3).
- Task 4: Core Audio listener blocks added from Swift cannot be removed. `AudioObjectRemovePropertyListenerBlock` returns `noErr`, but the listener keeps firing, whether the block is stored as `AudioObjectPropertyListenerBlock` or as `@convention(block)`: Swift hands Core Audio a new block on every call (tested on macOS 27 with a per-process property). The recorder registers its default-input listener once and captures `self` weakly. Task 24's device-list observer should do the same, or use the function-pointer API (`AudioObjectAddPropertyListener`).
- Task 4: `installTap`'s buffer size is clamped to 100–400 ms (`AVAudioNode.h`), so `onLevel` fires about 10 times a second and the first buffer arrives about 100 ms after the engine starts. Task 17's `LevelLine` pushes a vertex every 50 ms, so roughly every other interval gets no new peak.
- Task 4: `AVAudioEngineConfigurationChange` is posted on the engine's internal queue, and tearing the engine down from the handler can deadlock (`AVAudioEngine.h`). The Task 2 recorder observed on `.main` and tore down inside the handler; the recorder now observes with `queue: nil` and does the work in a `DispatchQueue.main.async` block.
