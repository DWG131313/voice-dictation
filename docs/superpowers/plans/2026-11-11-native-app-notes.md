## Findings

- Task 9 (fix round 1): The app's own Cmd+V is tagged. `PasteEngine` sets `.eventSourceUserData` to `PasteEngine.eventTag` ("VDPASTE" in ASCII) on the key-down and key-up it posts. The Globe key's event tap passes a tagged key-down through without consulting the press (`GlobeKeyStrategy.action(forKeyDown:sourceUserData:presses:)`). This is needed because the pipeline pastes a dictation as soon as its text is ready, which can be while the hotkey is held for the next one, and the tap sees that Cmd+V like any other key. Task 23's `ModifierKeyStrategy` must keep the rule for every hotkey choice, including while hands-free is locked. Paste last goes through `PasteEngine`, so it is tagged too. The CoreGraphics header says every event carries 64 bits of user data, settable per event (`CGEventSource.h`, `CGEventTypes.h`). That the tag survives from the HID tap, where it is posted, to the session tap, where it is read, is the Task 9 back-to-back hands-on check above.
- Task 9: What later tasks can rely on from `DictationPipeline`.
  - It does not clean up or apply replacements yet; it stores `cleaner` and `replacements` unused. Task 21 adds the cleanup step. `Replacements.apply` only arrives in Task 22, and Task 22's file list does not include `DictationPipeline.swift`, so whichever of them adds that function must also add the call, between the service's text and the cleaner. Task 9 passes `vocabulary()` to the service with each dictation.
  - Dictations go to the service as soon as each recording ends, so the service always sees every dictation in line and keeps re-transcriptions behind them. The pipeline pastes in recording order. When a fifth arrives with three waiting, the second-oldest in line is skipped. Its call to the service is cancelled while it waits, so its outcome (Failed, with the clip and "Skipped: too many dictations waiting") comes a moment later, usually before the outcome of the dictation being transcribed. One narrow case is kept by ruling, because its window is one main-actor hop. The pipeline counts the dictation at the head of its line as being transcribed until it has taken that dictation's result on the main thread. A fifth recording that ends after the service has returned the head's result, but before the pipeline has taken it, still skips the second in line. Yet only three are then waiting at the service, and the skipped dictation is already in the engine. So the effect is a skip that should not happen, of a clip that has already reached the engine.
  - Two cancels. The hotkey uses `cancelHold()`: a key pressed while Globe is held (Globe+Right Arrow, or Escape) cancels this hold's dictation and nothing else. That is the recording under way or, when the recorder ended the recording by itself while Globe stayed down (300 s, or an input change), the dictation it became, until Globe goes up. After a failed start, or a recording the recorder threw away, it cancels nothing. So Globe+Right Arrow never stops an earlier dictation from pasting. `cancel()` is for Task 23's Escape while working: while recording it cancels only that recording; otherwise it cancels every dictation in line.
  - `missingPermission` (set by the app from `PermissionManager`) is what the state falls back to after an error. `selectModel(_:named:downloadingFirst:)` shows `.preparingModel(name)` while a model downloads and loads. A failure there is shown as an error and rethrown, and the caller saves the choice only on success.
  - An outcome's `date` is when its recording ended; the comparison file name uses it, as Task 2's did. `appName` is the frontmost app when the dictation finished: at the paste, or for a failure when it failed.
  - Comparison recordings (Rulings T9-1, T9-2): while the setting is on, every dictation that was not cancelled leaves a `<ms stem>.wav` and `<ms stem>.txt`, as Task 2's writer did. One with an outcome is written from `onOutcome`, its `.txt` holding the outcome's `rawText` (empty for a failure). A dictation whose text came back empty has no outcome. The pipeline reports its clip and the time its recording ended through `onNothingHeard`, and its `.txt` is empty. If Task 24's audio archive must keep those clips too, it needs `onNothingHeard` as well as the outcomes.
  - SDK facts used for the wiring: `Observations` (Observation, macOS 26) yields the current value first, then each change, and merges changes made in one main-actor turn. A script on this SDK saw `[1, 2, 4]` for changes to 1, 2, then 3 and 4 in one turn. Conforming a main-actor class to a delegate protocol with `@preconcurrency` inserts no run-time isolation check in Swift 5 mode; it relies on the caller using the main thread, which the recorder and managers do.
- Task 8 (fix round 1): `Log.info` no longer writes `~/Library/Logs/VoiceDictation.log` under XCTest (Ruling T8-3); test runs only print their lines, so look for them in the test output, not in the log. `prepareSelected` now keeps a saved choice whose engine is gone as `engineUnavailable` (`prepareFailure(of:)`) and logs it, which matters once Task 27 retires whisper-cli while a migrated `whisperCLI/…` choice is still saved. The cancellable wait the service and WhisperKit both use is one helper, `valueUnlessCancelled(of:)` in `Core/TaskWaiting.swift`.
- Task 8: What later tasks can rely on from `TranscriptionService`.
  - `elapsed` is the engine's time on the clip only. Waiting in line, waiting for the model to prepare, and an attempt a dictation stopped are not counted. If Task 9's `transcribeSeconds` should include a dictation's wait for a loading model, it needs its own clock.
  - A failed prepare is kept (`prepareFailure(of:)`, internal) and logged as `[SERVICE] Could not prepare …`, but it does not stick. The next dictation prepares the model again, so a model that becomes ready (for example after Apple's one-time Download) works without being chosen again.
  - `select` calls take effect one at a time, in call order.
  - Unloading is per engine (Ruling T8-1), and timed from the re-transcription lane (Ruling T8-2, fix round 1). An engine counts as in use from the moment a call for one of its models is made until that call returns, so a queued re-transcription keeps its engine loaded. An engine that holds a loaded model, is not in use and does not hold the selected model is idle only while no re-transcription is running or waiting; it is unloaded once it has been idle for `idleUnloadDelay`. So a run of re-transcriptions on several engines (Task 10's bench) keeps them all loaded until the lane empties, and they go `idleUnloadDelay` after that. `select` unloads the previous engine at once only when nothing is using it; otherwise the engine goes once it has been idle for the delay.
- Task 8: The old app saves `selectedModel` only when a model is chosen from its menu (`ModelManager.switchModel`). On a Mac where it was never changed there is nothing to migrate, and the new app starts on Apple Speech (the ruling sends a missing value to `.appleSpeech`). On this laptop neither the dev build's defaults (domain `VoiceDictation`) nor `com.danny.VoiceDictation` has a `selectedModel`. Task 6 found that each app must reserve Apple's language files once, with the Download button. Until that Download is pressed, the new app's first dictations here will fail with "Apple Speech language files are not installed", and Review Focus 1 keeps them as Failed with their audio. So the brief's aim, keeping the app working on first run without Apple's files, holds only on a Mac whose old app had a model chosen.
- Task 7 (fix round 1): deleting a model while it loaded made WhisperKit go to the network. The load kept running after `delete` removed the files. If it got past the Core ML loads once the tokenizer folder was gone, `ModelUtilities.loadTokenizer` fetched the tokenizer from huggingface.co and recreated that folder. The review's probe saw this when deleting 2.0–4.5 s into a 4.8 s cold tiny.en load. `delete` is now refused while the model prepares ("… is still preparing"), as it already was while it downloads. `unload()` no longer forgets a load in flight: the load runs to its end and the model still shows as Preparing until then, but it is not kept unless it is asked for again first. A tokenizer file that exists but fails to parse also triggers the network fallback, on every load, because the engine checks only that the files exist. That cannot be closed without bypassing WhisperKit's loader.
- Task 7 (fix round 1): with its default padding, WhisperKit's `VADAudioChunker` drops whatever follows the last split when that is 1 s or less, so a clip over 30 s could lose its last word. The review measured 0.5–0.9 s lost from 30.5–60.5 s clips; `testChunksKeepTheLastSecond` reproduced it (a 30.6 s clip came back as one 29.7 s chunk). The engine now chunks with no padding. It leaves out a final chunk of 1 s or less only when that chunk holds no voice (EnergyVAD finds none, or its peak is under the app's 0.01 floor), so a silent tail cannot decode to "you". With tiny.en, a 30.2 s clip split into 29.3 s and 0.93 s, the last 0.93 s holding a spoken "Yes.", came back ending in "Yes.".
- Task 7: WhisperKit is pinned `exact: "1.1.1"` (package `argmax-oss-swift`, released 2026-10-08). It was still the latest stable release on 2026-11-12: the release list and the tags have nothing newer. `Package.resolved` adds only swift-argument-parser 1.8.2, its sole dependency. The four model folders exist on `argmaxinc/whisperkit-coreml` (checked 2026-11-12), with these download sizes: `openai_whisper-tiny.en` 153 MB, `openai_whisper-base.en` 147 MB, `openai_whisper-small.en` 487 MB, `openai_whisper-large-v3-v20240930` 1.6 GB. tiny.en is larger than base.en because its folder also carries `.mlpackage` copies, and WhisperKit downloads the whole folder. `openai_whisper-large-v3_turbo` is 3.2 GB, consistent with it being full large-v3. In v1.1.1's built-in model list, `openai_whisper-large-v3-v20240930` is the default for M2, M3 and M4 Macs.
- Task 7: WhisperKit never decodes a window of 1 s or less with its default `windowClipTime` (1.0 s), and returns "" without running the model. A 0.65 s "Yes." and a 0.75 s "Okay." came back empty, and the app keeps every recording of 0.5 s or more. The engine sets `windowClipTime` to 0; both words then came through, and longer clips were unchanged. `testShortClipIsTranscribedWhenTinyIsPresent` pins this. With it, 1 s of silence gives "you", which `OutputFilter` drops in the service.
- Task 7: WhisperKit's own `.vad` chunking strategy (for clips over 30 s) drops any chunk that fails, with only a debug log, so the text would silently miss part of the dictation. The engine splits the clip with WhisperKit's own `VADAudioChunker` and transcribes the chunks with `transcribeWithOptions`, which returns each chunk's result; a failed chunk fails the whole transcription. A 52.5 s clip of 14 different sentences came back complete in 0.36 s with tiny.en. A cancelled chunk also comes back as a failed result rather than a throw, so the engine checks for cancellation itself; a 2-minute transcription cancelled 0.3 s in stopped 7 ms later.
- Task 7: Where the files go: models in `<root>/models/argmaxinc/whisperkit-coreml/<folder>/`, the Hub client's records and partial downloads in `<root>/models/argmaxinc/whisperkit-coreml/.cache/huggingface/download/<folder>/`, and each tokenizer (`config.json`, `tokenizer_config.json`, `tokenizer.json`, 2.3 MB) in `<root>/models/openai/whisper-<size>/`. Nothing went to `~/Documents/huggingface`. Loading needs no network: with `HF_ENDPOINT` pointed at a closed local port, the first load and later loads of tiny.en both succeeded. A model counts as downloaded only when its three Core ML models, `tokenizer.json` and `tokenizer_config.json` are all there; `delete` and a failed download remove all three folders.

- Task 6: An analyzer that was never prepared and is handed an input sequence with no buffers never ends its module's `results`, even after `cancelAndFinishNow()`. The engine returns "" for an empty clip without building an analyzer, and prepares every analyzer it builds. A prepared analyzer cancelled mid-clip ends its results at once.
- Task 6: Both models want 16 kHz mono 16-bit input here; the engine converts each clip's float samples once. - Task 4: Core Audio listener blocks added from Swift cannot be removed. `AudioObjectRemovePropertyListenerBlock` returns `noErr`, but the listener keeps firing, whether the block is stored as `AudioObjectPropertyListenerBlock` or as `@convention(block)`: Swift hands Core Audio a new block on every call (tested on macOS 27 with a per-process property). The recorder registers its default-input listener once and captures `self` weakly. - Task 4: `installTap`'s buffer size is clamped to 100–400 ms (`AVAudioNode.h`), so `onLevel` fires about 10 times a second and the first buffer arrives about 100 ms after the engine starts. Task 17's `LevelLine` pushes a vertex every 50 ms, so roughly every other interval gets no new peak.
- Task 4: `AVAudioEngineConfigurationChange` is posted on the engine's internal queue, and tearing the engine down from the handler can deadlock (`AVAudioEngine.h`). The Task 2 recorder observed on `.main` and tore down inside the handler; the recorder now observes with `queue: nil` and does the work in a `DispatchQueue.main.async` block.
